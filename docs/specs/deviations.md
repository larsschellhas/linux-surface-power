# Deviations from Windows behaviour

Version 0.7, 28.11.2026 (0.7: DV-8 and DV-10 after the tester reports of 27.–28.11.; 0.6: DO-1 does not act under the unit, B15; 0.5: DV-3 after the Windows trace; DV-8 after the module tests on the SB3, DS-5; 0.3: the MMIO path implemented; 0.4: DV-2 and DV-12 for absent base sensors, B13). Implements G-3, NFR-10, AC-X3. Every known or possible difference between this implementation and Windows'
SMF is listed here. Intended improvements are opt-in and off by default; none exists yet (ideas in `../requirements/ideas.md`).

## 1. Unavoidable (no Linux counterpart)

| ID | Difference | Effect | Default |
|---|---|---|---|
| DV-1 | Temperatures are polled every second. Windows reads them only when the EC trip point (42 °C on the SB3) is exceeded, and holds the last value below it. | None for control: every controller is OFF far above 42 °C. Below the trip point, Linux sees current values where Windows holds an old one. | always |
| DV-2 | KIP/base temperatures (600 + iid) exist only while the SB3 base is attached (kernel nodes since kernel#190, 17.11.2026). Without the base they are absent (`supervisor.md` 4.1): invalid, block defaults, no emergency; as on Windows, where the base thermal client is removed with the base [C]. | Controller 4 (dGPU) OFF, the base part of the thermal actions gives no request; the limits stay in control. The look-up after a re-attach takes up to 5 s. | while the base is detached |
| DV-3 | Display brightness in nits is not provided. On the SB3 15" the Windows client did not query it either in the measured state (`inputs.md` 5). | PL4 uses 3 W display power (the block default without a value). On the SB3 15" the same as Windows, or PL4 3 W lower if the core read the client's start status as 0 [H]. Other devices with channel 41: not measured. Accepted by the maintainer 26.11.2026 (plan G1). | channel invalid |
| DV-4 | Slider states 8 – 10 (game mode, mixed reality, service flag) do not exist on Linux. Low-power on AC maps to Recommended. | Linux never selects these states. | fixed mapping (OD-4) |
| DV-5 | The dGPU limit, WTMF and fan outputs have no Linux target. On the SB3 (GTX 1660 Ti, driver 595), `nvidia-smi -pl` is refused with or without persistence mode, and Dynamic Boost (`nvidia-powerd`) needs Ampere or newer; the driver reports it as not supported. | Computed and logged only. A clock-cap stand-in is a backup concept (I-4). | log-only |
| DV-6 | `0x53` data comes from requests instead of EC events. | Values are fresher than on Windows (where events sometimes did not arrive). | always |
| DV-7 | `87008365/112` (called "averaged" CPU temperature) is the instantaneous `coretemp` package temperature. The Windows SoC client takes one reading of the same register (package thermal status, MSR 0x1B1, bits 22:16) per request and converts it with TjMax to 0.1 K; it holds no average and no window [C, client driver of the Pro 10]. Linux gives the same reading with the same 1 K steps. A filter in the SMF core was not found [M]. | Expected to be none. Only the fan noise floor `B620798F/121` above ~71 °C uses it. | on |
| DV-8 | PL1/PL2 (and the PL1 time window) go to the MSR copy (`0x610`, powercap). Windows writes the MMIO copy (MCHBAR + `0x59a0`) with enable and clamp set; `intel-rapl-mmio` needs the processor thermal device, which is absent on the SB3 and a Pro 10 (`outputs.md` 3.3). | The lower copy is in force: lowering works as on Windows; raising above the firmware's MMIO value has no effect where that copy is enabled (Pro 10: 28 W instead of 30 W, measured with the MSR copy at 30.0, 29.2, 27.3 and 25.5 W: package power 28.0, 28.0, 27.6, 25.5 W, one tester, one device [M]; Pro 8: 30 W instead of the blob's 35 W [M]; Pro 8 Windows value 35 W is derived, not measured; Pro 9 Intel: firmware MMIO 30/60 W enabled, MSR 35/60 W [M], so Slider 5 on AC (blob 35 W) is capped at 30 W by the same rule [H] (in a tester's 56-hour dry-run on a Pro 9 the computed PL1 was above 30 W only on slider 5, about 35 s in all [M]); Pro 7+: MMIO and MSR both 30/60 W enabled [M, tester, 25.11.2026], while its blob allows up to 31/62 W). PL2 follows the same rule [H, not measured]. On the SB3 15" the firmware leaves the MMIO copy disabled (enable bits 0, PL1 clamp 1, lock bits 0, [M] 23.11.2026), so the MSR copy alone is in force [M]; a limit written into the disabled copy has no effect, and with the copy enabled through the test module an 8 W PL1 held the package at 8.0 W against the MSR copy's 30 W (24.11.2026, `kernel-mmio-rapl.md` 5.4) [M]: the lower enabled copy is in force on four devices now (Pro 10, Pro 8, Pro 9 Intel, SB3), still [H] as a general rule. With the firmware's own enabled copy, full load settled at the MMIO PL1 below the MSR PL1 on a Pro 10 (28.0 W against 35 W), a Pro 8 (29.9 W; MMIO 30, MSR 35) and a Pro 9 (29.6 W; 30, 35); on the Pro 10 and the Pro 8 a lower MMIO PL1 written through the module (23 and 24 W) was then held (23.0 and 23.9 W) and the register was bit-identical after the unload [M, testers, tester kit, 27.–28.11.2026, issues #3, #4, #7 of this repository]. A Laptop 4 Intel 15" has its MMIO copy enabled at 30/60 W, equal to its MSR PL1/PL2; under load it was held by the firmware's psys PL1 45 W (package 27.8 W), not by PL1 [M, one tester, 27.11.2026, #6]. The MMIO copy is neither changed nor restored by the daemon. `surface-power-report` (as root) shows it; the daemon's 60-second log and `status.json` show it only with `CAP_SYS_ADMIN`, so **not under the packaged units** (plan B11, `kernel-mmio-daemon.md` 8). Windows' own effective limit also includes the firmware MSR value [H]. **MMIO path (KM-9, `kernel-mmio-daemon.md`, implemented 24.11.2026, checked on the SB3 the same day: 9.98 W at a 10 W MMIO PL1 with the MSR copy at 30 W [M]):** where the module (with `allow_write=Y`) or the kernel provides a writable zone, the daemon writes the MMIO copy and leaves the MSR copy at its snapshot value, which removes this deviation on that device; the MMIO copy is then snapshotted and restored. On the `msr` path the daemon now reads the copy from a zone too where one exists. Differences that stay on that path: where the firmware already enabled the copy, the daemon does not set the clamp bits (Windows ORs them into every write [C]; their effect there is [H], on the SB3 the clamp has none [M]); the module writes 64 bits where Windows uses 32-bit accesses in most tables [H]. | always on the `msr` path |
| DV-9 | PL3 (`0B7B5350/59`) is written only where a profile switches it on. Windows writes it on every Intel device with a CPU client. Verified devices without a matching profile log it only. | Peak platform power keeps the firmware value there (on the SB3 that would be 65 W instead of 100 W on AC). | per profile (`outputs.md` 4) |
| DV-10 | The SAM temperature sensors (`2E8B14C2/505, 509`, …) have a Linux source only where the kernel registry instantiates the TMP sensor node `01:03:01:00:02` (`surface_temp`, hwmon `surface_thermal`). In linux-surface `v7.3-surface-devel` (read 23.11.2026) it is missing for the Pro 7+, Pro 8, Laptop 3/4 AMD, Laptop 4 Intel, Laptop 7, Laptop Go 1/2/3 and Laptop Studio 1 [C]. Reported on a Laptop 4 Intel 15" (tester, 20.11.2026 and 27.11.2026, stock kernel; the registry is the same on linux-surface). Read-only probes answered on the Pro 8 (mask `0x07ff`, 1983) and the Laptop 4 Intel 15" (mask `0x07f6`), including the sensors their blobs read (5 and 9), and the readings followed a load test [M, testers, 27.11.2026, #4, #6]. | The input is invalid, so every controller that reads it falls back to its block default and the daemon refuses control where the input reaches a written output. No substitute exists (the requests work through the debug device on the reporting device [M, one tester], but the daemon does not read the sensors that way). | until kernel nodes exist (`plan.md` D9, D10) |
| DV-11 | A SAM write (fan, charging, sensor offset, PROCHOT) is sent with flags 0: success means the request was sent and acknowledged on the link, not that the EC handled it. "Written" in the status and on the device pages therefore says "sent". The effect was measured for `FAN 0x0e`/`0x0f` (SB3), `FAN 0x0b` (Laptop Studio 2, tester) and for the offset `TMP 0x24` only by a tester with instance 0 instead of our instance = sensor (no handler read so far reads the instance, `outputs.md` 9.8). For `TMP 0x24` the package firmware shows what "sent" can hide [C, static, 27.11.2026]: Go 3, Laptop 5 and Pro 9 Intel have no handler, so the output does nothing there although it counts as written (the Laptop 5 blob writes +1.0 K; Windows' request does nothing either); on the Pro 10, Pro 11 Intel and Laptop 6 and 7 Intel the value is cut to whole kelvin, as with Windows' request. | No read-back; a request the EC ignores is not noticed. | always |
| DV-12 | Windows keeps the last value when a sensor read fails or is out of range (the client sends no update) and takes a client's channels offline together on a client failure or removal [C, raw note `b13-basis-sensoren-2026-11-24.md` 2]. Linux marks a failing channel invalid at once. | Linux falls back to the block defaults earlier on read errors. Not reproduced: an old, cool value would stay valid for ever on a broken sensor [D]. | always |

## 2. Unknown details, chosen by us

| ID | Point | Our choice | How to verify |
|---|---|---|---|
| DH-1 | Which input changes trigger an asynchronous run | any change in value or validity of an input the instance reads | replay comparison with Windows traces |
| DH-2 | When the timer starts and stops | after every run, it follows the `active` flag of that run; first timer run one period after the start | Windows ETW trace of the SMF core |
| DH-3 | Timer run and input change in the same second | one timer run | as above |
| DH-4 | Internal nodes shared between instances 0 and 1 | shared | no blob uses instance 0 |
| DH-5 | Input readings outside the channel range | invalid | Windows client behaviour on range errors: the value is dropped and the last one kept [C client, H core], DV-12 |
| DH-6 | Cores 3.141 – 3.158 | `classic` variant | read such a core, if one turns up |
| DH-7 | Charge rate while charging | 0 | read the power-tracker client |
| DH-8 | Elapsed time of the first EWMA update (engine 5.5). Windows counts it from loading the blob. | counted from the first run, so the first update keeps the default | Windows ETW trace |
| DH-9 | EWMA in core 3.204.23 (Pro 10) has no `Δt ≥ τ` rule and overshoots after long gaps | the rule of cores ≥ 3.205.6 for all cores | differs only when a run comes more than τ after the last |
| DH-10 | State of the newer blocks (engine 5.1 – 5.5) on resume | kept | read the core's resume path |

## 3. Safety additions (not in Windows)

| ID | Addition | Default |
|---|---|---|
| DS-1 | Hard limits in the output stage (`outputs.md` 2) | on, cannot be widened |
| DS-2 | Emergency rules (`supervisor.md` 4) | on |
| DS-3 | Yielding to foreign changes (`supervisor.md` 5) | on |
| DS-4 | Firmware values before suspend | on |
| DS-5 | Restore of the MMIO copy through its zone (implemented 24.11.2026, `kernel-mmio-daemon.md` 5.2). Limitation: on a copy the firmware left disabled with PL1 clamp 1 (SB3 [M]) the restore writes `enabled=0`, which clears that clamp too; the zone cannot set single bits. Same effect as the firmware state on the SB3 (no limit either way [M]); the module's restore at unload, a cold boot or a warm restart brings the bit back [M, one cycle each]. Logged once. | with the MMIO path |
